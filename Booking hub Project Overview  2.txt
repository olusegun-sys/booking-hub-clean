## 🎯 Project Vision & Mission

### What We're Building

**Plazzaa** (formerly Booking Hub) is a multi-tenant booking management platform for Nigerian businesses. Think of it as **"Shopify for bookings"** — not a marketplace like Booking.com, but a platform where each business gets their own branded booking page, accepts payments (Paystack or pay-at-venue), receives automated email notifications, and tracks all bookings in a real-time dashboard.

**Part of the Plazzaa ecosystem:** The platform is the "Plazzaa for Business" solution — a comprehensive business management tool. The product was rebranded from **Booking Hub** to **Plazzaa** on 18–21 September 2026.

### Major Strategic Pivot: From Hospitality-Only to Any Business Type

As of the 14 September 2026 meeting, the platform serves three groups:

- **Stays** — Hotels, apartments, event halls
- **Food** — Restaurants, diners, cafés, catering, other food
- **Others** — Sports facilities, spas, beauty salons, nail studios, car washes, activity places

The dashboard, signup flow, landing page, emails, homepage, and booking page all adapt per business type via a **config-driven label system**.

### The Reconciliation Decision (7–15 October)

**Two competing designs, one clear answer:**

- **Emmanuel's design** — polished, animations, editorial, beautiful merchant dashboard, but built for a single business type (services with slots). No admin dashboard route, no multi-type support, no RoomPage.
- **Our design** — functional, config-driven, 15+ business types, admin dashboard, RoomPage, everything works. Less visually polished.

**The decision:** keep both. Merge at the seams.

**The rule:** *Emmanuel's paint, our plumbing.*

### Data Flow — Customer Booking

**Legacy path (default on live):**
1. Customer visits `/book/{slug}`
2. Our `UnifiedBookingPage` loads → business-type-aware labels
3. Select item → single date → confirm
4. `POST /api/bookings` → backend creates booking → sends email
5. Receipt modal → **Download Receipt** → PNG saves
6. Business sees booking in `/dashboard`

**Plazzaa path (testable at `/plazzaa-book/{slug}`, becomes default after Seam 5):**
1. Customer visits `/book/{slug}`
2. His `BookingPage` loads → 4-step flow (Service → Time → Details → Payment)
3. Bank-transfer confirmation
4. Merchant validates from their dashboard

**Post-Seam 5 plan:** his visual language + our multi-type logic, on one page.

### Data Flow — Homepage

**Legacy (default):**
1. `HomePage` mounts → `GET /api/businesses`
2. Backend returns approved + active businesses with `rooms[]`
3. Cards show real images (cover_image → logo_url → rooms[0].images[0])
4. Click → `/book/{slug}`

**Plazzaa (after Seam 2):**
1. `Landing` mounts → scroll-linked marketing page
2. "Explore" links to `/explore` (browse real businesses, uses legacy backend)
3. Not directly connected to the business list yet — this is a Seam 3/5 job

## 📁 Database Schema

*(Unchanged from 5 October — but a bug was found: the `is_active` column referenced in the backend doesn't actually exist in the DB.)*

### Tables

```sql
-- Businesses
CREATE TABLE businesses (
  id UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
  name VARCHAR(255) NOT NULL,
  slug VARCHAR(255) UNIQUE NOT NULL,
  business_type VARCHAR(100),  -- 15+ types
  description TEXT, email VARCHAR(255), phone VARCHAR(50),
  address TEXT, state VARCHAR(100), city VARCHAR(100),
  logo_url TEXT,           -- primary image source
  cover_image TEXT,        -- legacy, still respected
  about_text TEXT,
  status VARCHAR(50) DEFAULT 'pending',  -- pending | approved | rejected
  -- NOTE: is_active column referenced in server.js but does not exist in DB
  booking_limit INTEGER DEFAULT 50,
  current_booking_count INTEGER DEFAULT 0,
  subscription_status VARCHAR(50) DEFAULT 'free',
  ref_id VARCHAR(50) UNIQUE,
  custom_domain VARCHAR(255),
  is_domain_verified BOOLEAN DEFAULT FALSE,
  created_at TIMESTAMP DEFAULT NOW()
);

-- Rooms (generic "items" table)
CREATE TABLE rooms (
  id UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
  business_id UUID REFERENCES businesses(id) ON DELETE CASCADE,
  name VARCHAR(255) NOT NULL, description TEXT,
  price_per_night DECIMAL(10,2) NOT NULL, base_price DECIMAL(10,2),
  capacity INTEGER, images JSONB DEFAULT '[]'::jsonb,
  status VARCHAR(50) DEFAULT 'available', type VARCHAR(50),
  features JSONB DEFAULT '[]'::jsonb,
  amenities JSONB DEFAULT '[]'::jsonb,
  area_guide JSONB DEFAULT '[]'::jsonb,
  created_at TIMESTAMP DEFAULT NOW()
);

-- Bookings
CREATE TABLE bookings (
  id UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
  business_id UUID REFERENCES businesses(id) ON DELETE CASCADE,
  room_id UUID REFERENCES rooms(id) ON DELETE CASCADE,
  booking_reference VARCHAR(255) UNIQUE NOT NULL,
  customer_name VARCHAR(255) NOT NULL,
  customer_email VARCHAR(255) NOT NULL,
  customer_phone VARCHAR(50),
  check_in_date DATE NOT NULL,
  check_out_date DATE NOT NULL,
  total_amount DECIMAL(10,2) NOT NULL,
  payment_method VARCHAR(50),
  payment_status VARCHAR(50) DEFAULT 'pending',
  status VARCHAR(50) DEFAULT 'pending',
  created_at TIMESTAMP DEFAULT NOW()
);
```

### ⚠️ Schema Issues

1. **`is_active` column doesn't exist** — backend query was 500'ing until we removed the filter. Fix: either add the column via migration or keep it removed. Currently removed.
2. **v1 migration not applied** — `plazzaa_v1_migration.sql` defines `services`, `availability`, `blocked_slots` tables. Not yet run. His v1 backend uses a compatibility layer over `rooms` until then.
3. **The `rooms` table is overloaded** — serves as both "hotel rooms" and "services". Long-term this may need to split, but it works for now.

### Design Notes

- **`rooms`** is a misnomer — it's the generic "items" table
- **`business_type`** drives the entire label system — values must match across all maps
- **Image fields:** `logo_url` (current primary), `cover_image` (legacy), `rooms[].images[]` (per-item)

40. **Legacy Fallback Routes** — every old page kept reachable at `/legacy-*` during the reconciliation, so nothing breaks even mid-merge.

43. **`getBusinessToken()` Helper** — legacy components use a fallback chain to read the correct token even during partial migrations.
44. **Compatibility Over Perfection** — we accept that his design doesn't yet support multi-type. Reconciliation is additive; nothing is blocked on it.
