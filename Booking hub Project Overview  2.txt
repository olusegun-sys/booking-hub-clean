## 🎯 Project Vision & Mission

### What We're Building

**Plazzaa** (formerly Booking Hub) is a multi-tenant booking management platform for Nigerian businesses. Think of it as **"Shopify for bookings"** — not a marketplace like Booking.com, but a platform where each business gets their own branded booking page, accepts payments (Paystack or pay-at-venue), receives automated email notifications, and tracks all bookings in a real-time dashboard.

**Now part of the Plazzaa ecosystem:** The platform is the "Plazzaa for Business" solution — a comprehensive business management tool. The product has been rebranded from **Booking Hub** to **Plazzaa** as of 18–21 Sept 2026.

### Major Strategic Pivot: From Hospitality-Only to Any Business Type

As of the 14 Sept 2026 meeting, the platform serves three groups:

- **Stays** — Hotels, apartments, event halls
- **Food** — Restaurants, diners, cafés, catering, other food
- **Others** — Sports facilities, spas, beauty salons, nail studios, car washes, activity places

The dashboard, signup flow, landing page, emails, homepage, and booking page all adapt per business type via a **config-driven label system** (see "Business-Type-Aware System" below).

### Data Flow — Booking

1. **Customer** visits business booking page (`myplazzaa.com/book/{slug}` or custom domain)
2. Customer selects item/date → chooses payment method
3. **Frontend** sends booking request to backend API
4. **Backend** validates → creates booking in database → triggers email (business-type-aware)
5. **If Paystack**: redirects to payment → verifies on callback → confirms booking
6. **If Pay at Venue**: creates booking immediately → sends confirmation email
7. **Business Owner** sees booking in dashboard → manages status

### Data Flow — Business Search

1. User clicks a category card (**Stays / Food / Others**) on HomePage
2. Frontend sends comma-separated types for the group:
   - `stays` → `hotel,apartment,event_hall,event`
   - `food` → `restaurant,diner,cafe,other_food`
   - `others` → `sports,spa,beauty_salon,activity_place`
3. Backend splits into array, uses `.in('business_type', types)` when >1
4. Results returned and rendered with group-aware images and labels

### Data Flow — Business Signup

1. Business visits `myplazzaa.com` → clicks "Become a Host" or "Get Started"
2. **BusinessSignup.jsx** — 2-step flow: Account details → Location
3. Business type selected from grouped dropdown (Stays / Food / Others)
4. Backend creates `businesses` row with `status: 'pending'`
5. `sendWelcomeEmail` fires (uses `bookings@myplazzaa.com` sender)
6. Admin approves via dashboard → `sendApprovalEmail` fires with live booking link

### Data Flow — Auth (Scoped Tokens) 🆕

**Before 21 Sept:** Both admin and business logins wrote to the same `auth_token` localStorage key. Logging into a business overwrote the admin token; logging out of a business wiped both.

**After 21 Sept:** Scoped tokens.

| Session | Storage Key | Used By |
|---------|-------------|---------|
| Admin | `admin_token` | `/api/admin/*` routes |
| Business | `business_token` | All other API routes |
| Legacy fallback | `auth_token`, `token` | Read-only migration path |

**Data flow:**
1. Admin login → `AdminLogin.jsx` writes `localStorage.setItem('admin_token', data.token)`
2. Business login → `BusinessLogin.jsx` writes `localStorage.setItem('business_token', data.token)`
3. `AdminDashboard.jsx` reads `admin_token` first (fallback to legacy)
4. `BusinessDashboard.jsx` reads `business_token` first (fallback to legacy)
5. Logout clears only the scoped key it belongs to
6. On 401, each dashboard clears only its own scoped key

### Business-Type-Aware System

The core architectural pattern used across the platform: **one config map, keyed by `business_type`, drives all visible labels.**

Five places this exists:
- **`client/src/HomePage.jsx`** — `categoryGroups`, `businessTypeToGroup`, `businessTypeDisplay` maps
- **`client/src/UnifiedBookingPage.jsx`** — `BOOKING_LABELS` config for the public booking page
- **`client/src/HostLanding.jsx`** — hero/features/pricing copy adapted for all types
- **`client/src/BusinessDashboard.jsx`** — `getBusinessTypeConfig()` covers 15+ types 🆕
- **`server/src/services/emailService.js`** — `BOOKING_EMAIL_LABELS` config for email templates

Each map has an entry for every supported business type + a `_default` fallback for unknown types. Adding a new business type = adding an entry to each map. No if/else chains, no order bugs, no branches that silently fall through.

**Full business types supported (as of 21 Sept):**
- **Stays:** `hotel`, `apartment`, `event_hall`, `event`
- **Food:** `restaurant`, `diner`, `cafe`, `other_food`
- **Others:** `sports`, `spa`, `beauty_salon`, `salon` (legacy), `nails`, `car_wash` / `car-wash` / `carwash`, `activity_place`

### Design notes on schema

- **`rooms` table is a misnomer** — it serves as the generic "items" table for every business type.
- **`check_in_date` / `check_out_date`** are generic date fields — "the date of the booking" for every business type.
- **`business_type`** drives the entire adaptive label system. Values must match exactly between `BusinessSignup.jsx`, `HomePage.jsx`, `UnifiedBookingPage.jsx`, `HostLanding.jsx`, `BusinessDashboard.jsx`, and `emailService.js`.
